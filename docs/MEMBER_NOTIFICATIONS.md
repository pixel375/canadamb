# Member profiles and notifications

The same account works on CanadaMB and BrandonMB. `/users/{id}` shows the member's display name, join month, and site-visible listings when enabled. Members choose whether to publish their bio and Manitoba city in `/account/settings`. Keep email, password changes, and notification preferences in the signed-in account. City preference does not change which listings or notices belong to a portal.

`/account/notifications` groups moderation outcomes in **System & approvals** and followed discussion replies and Marketplace messages in **Social & activity**. Discussion and Marketplace message preferences control optional activity. Moderation outcomes remain available to their intended recipients. CanadaMB aggregates eligible Manitoba and province-wide records. Brandon shows eligible Brandon records. Followed discussion replies keep their existing read timestamps. Email and push delivery remain disabled.

Notices store recipient and source IDs, timestamps and geographic coverage. The inbox checks the current source, module, membership and conversation access before rendering links and again before opening them. Unavailable items have a generic description and contribute no unread count. The message inbox's existing read markers also clear effective unread counts. Historical notices are retained without a timed purge. New notices cascade on recipient deletion, while older notices keep their existing database relationship to the original reply.

The PWA worker, manifest and icons do not read or save the member session, so background installation requests cannot consume form feedback. These endpoints still use the existing host and prelaunch policies.

## Schema and migration review

- `2026_11_21_000001_create_member_settings_table.php` creates one optional private settings row per member. Existing accounts use default settings until they save changes.
- `2026_11_21_000002_create_notification_inbox_tables.php` creates `notifications` and `notification_locations`. The recipient, event and source key prevents duplicate inserts. Recipient/read/order indexes support inbox queries, and the location table supports lookup in either direction.
- The inbox reads legacy `community_notifications` in place. There is no backfill, schema alteration of that table, or seeder change. Read actions update the stored read state for the owning member. Validate the legacy route and read action as part of acceptance.

Verify CanadaMB runs `bash tests/Deployment/hostinger-release.sh production-pass-02` after building the candidate artifact. It installs the exact Pass 01 baseline in a disposable MariaDB schema, seeds a read and an unread legacy notice, checks the default migration denial, previews the pending SQL, and exercises the guarded upgrade with explicit approval confined to the disposable database. It compares legacy rows and schema, checks the new indexes and empty new tables, and restores the resulting pre-update SQL and media backups into separate disposable locations. The upgraded inbox reads the original notices and their read states. Two independent reviewer processes also compete for one reply decision and verify that only one set of notices is written. Review the result on the intended SHA in CI.

On Hostinger, the guarded deployment defaults to rejecting migration and seeder changes. Obtain explicit approval for the reviewed migration and exact SHA before merging into the deployment branch. Check the exact production DB name, retained SQL and media backups, backups' checksums and the migration preflight in the authorized release. Keep the prelaunch IP gate, credential configuration, and registration default unchanged during the release. [Deployment checklist](DEPLOYMENT_CHECKLIST.md#pass-02-member-settings-and-inbox-release-checks) · [Hostinger runbook](HOSTINGER_DEPLOYMENT.md)

If migration or later verification fails, keep traffic in maintenance and cron paused until the schema and logs are reviewed. MariaDB can commit DDL before a later step fails. Confirm schema compatibility before switching the code pointer to the previous release. Review a forward fix or an authorized restore if compatibility fails. Preserve failure evidence and establish the recovery point before restoring a snapshot. Restoring the pre-update database discards writes made after that snapshot. A migration rollback would drop the new inbox and settings tables, including any new activity and preferences.

## Allowlisted owner checks

Use separate browser profiles for a super-admin and two controlled members. Record the live SHA, host, account role, fixture IDs, device, and result. Use the existing [Pass 01 procedure](AUTHENTICATION.md#pass-01-prelaunch-acceptance) if an authorized tester account needs creation or verification.

1. Sign in on CanadaMB, then sign in to Brandon through central SSO. On both hosts, open **My account** and **Notifications**. Confirm the same identity and settings, then test at phone width in light and dark mode, including from an already installed PWA.
2. Save a display name, a short bio, and a broad preferred city with both publication controls off. From a signed-out profile on the allowlisted network, confirm the member page hides bio, city and email. Enable each public field and confirm only the chosen fields appear. Test the listings toggle and compare approved Brandon and another Manitoba city's listing on the two hosts.
3. Use the existing review actions to approve or reject disposable Marketplace, business, job, discussion, and event submissions. Confirm only the intended member gets each expected notice, and repeat an unchanged review to check for duplicates. Send a Marketplace message between the controlled members and approve a followed discussion reply. Check the recipient, optional preferences, and absence of message body text in the inbox.
4. Open **All** and **Unread** on each portal. Confirm Brandon excludes other-city activity, CanadaMB includes eligible notices, and the legacy inbox route returns to the unified inbox. Mark a legacy and a new item read, then confirm the corresponding state on the other host. Mark all read from Brandon and confirm a CanadaMB-only unread notice remains. Verify the second member cannot read or change the first member's records.
5. Withdraw or hide a controlled source and confirm its notice no longer exposes private titles or an unauthorized link. On both hosts, verify private pages are unavailable when signed out and retain `Cache-Control: private, no-store` when signed in. Run the independent external prelaunch/PWA audit after release.
6. If testing password changes on a controlled account, confirm the current password is required, earlier sessions stop working, and the new password signs in on both hosts through central SSO. Record any remaining owner device checks separately from CI and deployment evidence.
