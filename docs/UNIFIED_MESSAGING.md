# Unified messages

Members open `/account/messages` to find Marketplace, business, and job conversations. The inbox shows unread counts, supports search and context filters, and uses the current portal's geographic scope. CanadaMB covers Manitoba. BrandonMB covers Brandon. Marketplace history follows the listing's location. Business and job threads use the location recorded when the conversation began.

Marketplace buyers contact sellers from visible listings. A verified business owner or manager can opt in as the contact for their branch or job in the corresponding account form. A new thread requires an active, visible source and an eligible contact. The sender and the assigned responder are the participants. A change in responder can create a new thread. Access to an earlier thread still belongs to its original participants, and a representative who loses their eligible business role loses access. Existing Marketplace conversations can continue after the listing closes.

A block prevents new sends in either direction, attachment access, and unread activity for that pair. Conversation reports accept a reason and an optional message from the other participant. A participant can file one report per conversation. The audit entry records identifiers. Account settings have independent in-app notice preferences for Marketplace, business, and job messages. Opening a message page records receipts for the incoming messages displayed there. Sending a reply leaves unseen messages unread.

Messages support up to three JPEG, PNG, WebP or supported static PDF attachments. The limits are 5 MiB per file and 12 MiB total. The application re-encodes images to WebP. Participants retrieve files through the conversation's private route. Images can display inline and PDFs download. The supported PDF subset uses one revision and a classic cross-reference table. It excludes interactive features, inline images, encrypted files, embedded files and unsupported compression. File paths are generated by the server and held in private storage. The orphan report `php artisan messages:attachment-orphans` lists eligible unreferenced attachments older than 24 hours for review. It performs a dry run.

## Schema and release rehearsal

`2026_11_22_000001_expand_unified_messaging.php` adds the context type and nullable branch, job and geographic references. The existing listing reference becomes nullable for the new contexts and keeps its foreign key and listing/buyer uniqueness. Business and job uniqueness is per source, sender, and responder. The migration adds optional contact assignments, independent notice preferences, nullable send tokens unique per sender, and private attachment and report metadata. `message_reads` stores exact message/reader receipts beside the legacy high-water marks. `message_send_replays` binds an early duplicate submission token to the message already sent. Legacy messages and read markers stay in their existing rows. Existing threads receive the Marketplace context and existing settings rows use the enabled defaults for the two new notice preferences.

Verify CanadaMB runs `bash tests/Deployment/hostinger-release.sh production-pass-04` against disposable MariaDB using the exact corrected Pass 03 baseline. It checks that the unapproved upgrade is rejected without a schema or release change, previews the SQL, and runs the guarded upgrade with approval for the disposable database. It compares legacy threads, message content, read markers, notices, preferences, and blocks. It verifies the new schema, checks the backup hashes, restores the pre-upgrade SQL and private storage into separate disposable locations, and holds a listing row while two independent PHP send requests arrive with the same token. Both requests must reach the same thread and produce one message and one recipient notice. The populated SQLite test also checks that the table rebuild keeps the original rows, indexes, and foreign keys.

## Production release and recovery

Review the migration SQL and rehearsal results for the exact candidate SHA. Obtain approval for the schema change on the named production MariaDB database before promotion. Use the guarded Hostinger upgrade, retain the checksummed SQL and private storage backups, and verify the recorded migration preflight before activation. Keep these backups private because they include message content and attachments. [Deployment checklist](DEPLOYMENT_CHECKLIST.md#pass-04-messaging-release-checks) · [Hostinger runbook](HOSTINGER_DEPLOYMENT.md)

If an upgrade fails after activation starts, keep maintenance and the cron pause in place while reviewing the migration state. MariaDB may commit earlier DDL before a later statement fails. Review a forward fix or a restore of the verified SQL and private storage together. Restoring the pre-upgrade snapshot discards activity after that snapshot. The migration refuses rollback when organization threads, attachments, reports or read receipts exist. Even an otherwise permitted rollback removes contact assignments, send tokens and the new notice preferences.

## Allowlisted browser checks

1. Use controlled accounts on CanadaMB and BrandonMB. Open an existing Marketplace conversation and compare its unread state on both eligible hosts. Send to a seller, use the inbox filters, and check that a conversation from another city is available only on CanadaMB.
2. Use a verified business owner or manager to opt in for a controlled Brandon branch and job. From a member account, start a conversation on each source and confirm the designated responder can reply. Use a different organization member to test direct thread and file URLs. Change or revoke the representative and confirm earlier messages stay scoped to the eligible original participants.
3. Send an image and a supported static PDF from a phone and desktop browser. Check the image preview, PDF download, private no-store headers, authorization, and file size limits. Try a mismatched extension and confirm a clear validation message.
4. Block the other participant, confirm both send directions and direct attachment URLs are denied, and check unread counts. Unblock and confirm normal access. File a report and retry it. Switch each message notice preference independently and confirm the recipient sees only the selected optional activity.
5. Record the live SHA, host, device, controlled account roles, fixture IDs, and result. Run the independent deployment and prelaunch checks for the reviewed release.
